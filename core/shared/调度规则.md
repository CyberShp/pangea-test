# 调度规则（primary 与通用 analysis-worker 共同引用，只存一份）

> 本文承载模式判定、任务契约与任务 id 生成规则。primary 和通用 worker **引用同一份**，避免逻辑两处漂移。
> 对应架构：§2.1、§2.2.1 自举协议、§6.2。判据为【推测】起草，交待办 A-3 审。

---

## 一、场景识别与任务契约
- 用户显式 `/mr-regression` 或 `/module-analysis` 时优先；自然语言意图进入同一流程。
- 每次正式分析先生成任务契约：模式、目标模块、仓库与版本、MR、组网、测试重点、可选材料、排除范围和工具缺口。
- 信息充分时直接分析；目标不清、仓库/MR 不可访问或关键输入冲突时才要求确认。

## 二、模式判定（速度型 / 深度型）

**判据（关键词信号，【推测】）**：
- → **深度型**：请求含"全量 / 系统性 / 复盘 / 评审 / 出用例集 / SFMEA / 覆盖"等。
- → **速度型**：请求含"讲一下 / 大概 / 快速看看 / 单点 / 是什么"等。

**冲突时优先级**（从高到低）：
1. 用户显式指定（完整/速度/`--fast`）；
2. 关键词判据；
3. `/module-analysis` 默认完整型；`/mr-regression` 默认聚焦回归流程。

**仍不明确**：统一**询问用户**，不擅自默认。

## 三、任务 id 生成规则（仅深度型需要）

- 格式【推测】：`{场景}-{对象slug}-{日期}`
  - `场景`：场景 skill 文件名去扩展名（如 `模块全量分析`）；
  - `对象slug`：分析对象，`/`、`:`、空格 → `__`，仅取符号/短名；
  - `日期`：运行环境提供的当日日期（`YYYYMMDD`）。本执行环境不自造时间戳，实际由 codeagent 环境注入（待办 T-5）。
- **碰撞处理**：若 `runs/<任务id>/` 已存在，**先问用户**：续跑（恢复）还是全新重挖。全新则 id 追加 `-2`（再撞则 `-3` …）。

## 四、DFX 路由
- MR 回归固定执行：原场景回归、改动功能验证、影响链回归、异常与恢复验证；再根据 diff、提交记录、源码和任务材料的代码信号加载相关 DFX 包。
- 模块全量分析执行全部六个能力包。资源与规格包先扫描，命中资源信号或用户强调后专项深挖。
- primary 按 obligation/range 分片调用同一个 worker；worker 只输出 strict fragment，primary 负责合并、SFMEA、严重度/可信度和黑盒用例。
