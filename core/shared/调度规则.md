# 调度规则（Dispatcher 与族 agent 共同引用，只存一份）

> 本文承载"模式判定判据"与"任务 id 生成规则"。Dispatcher 与族 agent（自举时）**引用同一份**，避免逻辑两处漂移。
> 对应架构：§2.1、§2.2.1 自举协议、§6.2。判据为【推测】起草，交待办 A-3 审。

---

## 一、场景识别
- 以用户意图为主，用户显式指定场景则优先。
- 场景清单与归属族见 Dispatcher 能力菜单表（architecture §2.1）。

## 二、模式判定（速度型 / 深度型）

**判据（关键词信号，【推测】）**：
- → **深度型**：请求含"全量 / 系统性 / 复盘 / 评审 / 出用例集 / SFMEA / 覆盖"等。
- → **速度型**：请求含"讲一下 / 大概 / 快速看看 / 单点 / 是什么"等。

**冲突时优先级**（从高到低）：
1. 用户显式指定（"我要深度分析" / "快速讲讲就行"）；
2. 关键词判据；
3. 场景典型模式（能力菜单表"典型模式"列）。

**仍不明确**：统一**询问用户**，不擅自默认。

## 三、任务 id 生成规则（仅深度型需要）

- 格式【推测】：`{场景}-{对象slug}-{日期}`
  - `场景`：场景 skill 文件名去扩展名（如 `模块全量分析`）；
  - `对象slug`：分析对象，`/`、`:`、空格 → `__`，仅取符号/短名；
  - `日期`：运行环境提供的当日日期（`YYYYMMDD`）。本执行环境不自造时间戳，实际由 codeagent 环境注入（待办 T-5）。
- **碰撞处理**：若 `runs/<任务id>/` 已存在，**先问用户**：续跑（恢复）还是全新重挖。全新则 id 追加 `-2`（再撞则 `-3` …）。

## 四、自举（族 agent 绕过 Dispatcher 直接进入时）
- 用户经 `@dev-expert` 等直接进入、未收到 `{场景, 模式, 任务id}` 时：族 agent 按**本文同一套**规则自行判定场景与模式、自生成任务 id。
- 判据只存本文一份，族 agent 不重复实现。
