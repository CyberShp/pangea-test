# 八问分析纲领（源码到测试）

本纲领是 `inventory → obligation → immutable context pack → analysis_fragment → semantic judge` 的分析最低面，不是聊天提纲。每个问题都必须由分配的 obligation 覆盖，并在 fragment 中给出源码证据、明确 disposition（已覆盖、N-A 或 `need_verify`）；没有证据不能用“未发现”结案。

## 八问

1. **责任与边界是什么？** 识别模块职责、对外契约、输入/输出、依赖和不变量；区分事实、推断和未决项。
2. **外部如何触发并完成注册？** 从 CLI、协议、API、事件、定时器或恢复入口追到注册/派发点；记录入口、调用者、前置条件和可达性。
3. **主流程与分支怎样运行？** 建立从触发到可观测结果的主路径，枚举成功、拒绝、降级和回退分支及其条件。
4. **状态与资源怎样变化？** 记录状态迁移、所有权、申请/释放、队列/计数/配额、持久化和销毁边界；说明谁负责恢复不变量。
5. **超时、重试与恢复如何闭环？** 覆盖超时源、取消、重试预算、幂等性、回滚、重连和最终恢复的外部判据。
6. **并发窗口与错误传播在哪里？** 标出共享状态、锁/原子/回调、初始化或销毁竞态；追踪错误生成、包装、吞没、上报、清理和潜伏故障。
7. **风险如何转成可执行黑盒验证？** 每个 High/Critical 风险给出外部触发、传播、业务后果、control、oracle、观测与恢复；证据不足时输出 `need_verify`，不伪造结论。
8. **证据、N-A 与未决如何可审计？** 每项结论绑定 snapshot、文件/范围、inventory id、obligation 和 capability/Storage Skill receipt。N-A 要写已查范围与具体不适用理由；未决项要写下一步验证方法。

## 执行纪律

- inventory 独立于分析生成，obligation 覆盖八问的适用部分；不能由 worker 自己缩减分母。
- 同一个通用 `analysis-worker` 只处理运行时分配的范围；按需要注入 capability pack 与 Storage Skill receipt，不把能力包变成人设。
- fragment 必须为 strict JSON；4096 截断、JSON 无效、漏 disposition、证据越出 context pack 或 receipt 不匹配均为失败。
- semantic judge 比较 obligation、证据和黑盒结论；合并者不能仅凭“已完成”文字给通过。
