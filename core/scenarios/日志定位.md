# 场景作业流程：日志定位

> 执行主体：primary（诊断工作流） ｜ 对应内网"问题根因辅助定位（时间线→异常传播链→候选根因）"｜ 模式：**速度型 / 深度型**
> 上游：[architecture.md](../../docs/architecture.md) §2.1（能力菜单/衔接表）、§8（深度型时序）｜ [requirements.md](../../docs/requirements.md) R-7.6、R-8.3
> **纪律**：本文只写"编排骨架"——即 primary 如何请求运行时冻结证据、重建时间线、组织候选根因。只有运行时生成有效 obligation/context pack 后才可调用固定 `analysis-worker`。**具体研判内功心法**（时间线怎么读、异常传播链怎么串、候选根因怎么排序）是内网资产，一律留 `<!-- 待迁移 M-4 -->` 占位，**不得凭简介重写**。

---

## 1. 场景定位

从外部日志证据反向重建内部故障链，定位候选根因。是 primary 诊断阶段的旗舰定位场景："日志里发生了什么 → 异常怎么传播的 → 根因可能在哪、怎么外部验证"。不臆断，候选根因严守溯源双轨制。

## 2. 输入（前置到 primary 收集）

- **日志片段**（用户粘贴）**或** 日志文件路径。大文件由 primary 的只读日志搜索/切片工具能力处理，不派发额外角色。
- **模式**：速度型（"帮我看下这段日志 / 快速定位"）或深度型（"复盘 / 系统定位 / 出定位报告"），判据见 `core/shared/调度规则.md` 二；不明确则问用户。
- **任务 id**（仅深度型）：`日志定位-<对象slug>-<日期>`（规则见 `core/shared/调度规则.md` 三）。

## 3. 编排流程

### 3.1 速度型（内联，不落工件）

粘贴片段或单点日志 → primary 内联读、内联定位，直接给候选根因（每个附证据引用 + 黑盒验证方法 + 置信度）。不建立独立日志工件、不建 `pangea-data/runs/`。研判细则留 M-4 占位。

### 3.2 深度型（冻结日志证据后分析，落工件）

1. **日志挖掘（primary 工具能力）**：primary 以只读 grep/解析能力按行号和时间窗切片，生成冻结 `log_summary`（schema §4.2a：`timeline`/`key_signals`/`correlations`/`raw_excerpts`，每条带 `raw_ref: log:<行号>`）。工具输出不是分析 Agent 结论。
2. **落盘（运行时职责）**：只可用 `runtime/diagnostic_artifacts.py --root <root> --run-id <任务id> --file <json>` 发布；类型固定为 `log_summary`，路径固定为 `internal/diagnostics/log-summary.json`，输入严格符合 `schemas/diagnostic-artifact.schema.json`（闭合字段、tool/status、至少一条 `log:<正整数>` 锚定证据）。运行时在 Run 级 flock 下，以 dirfd + `O_NOFOLLOW` 绑定物理祖先，经 durable journal 提交，并在 `internal/diagnostic-artifacts.json` 写入 `path/input_sha256/body_sha256/content_sha256/state=committed`。journal 或索引损坏、特殊文件、哈希冲突均失败；恢复只完成同一事务，不能用聊天文本替代。若需要结合源码解释日志，运行时从冻结日志证据和源码 inventory 建 obligations/ranges，再交同一 `analysis-worker`。
3. **重建故障时间线**：基于 `log_summary.timeline` 按时序还原故障演进（首个异常信号 → 传播 → 表征故障）。每个节点保留 `raw_ref` 锚点。**时间线解读话术留 M-4 占位。**
4. **异常传播链**：从时间线串出“异常如何产生 → 如何传播 → 如何处置/失控”。需要源码反证时，由运行时创建带冻结日志锚点的 `异常传播` obligation/context pack，`analysis-worker` 返回 `propagation_chains` fragment；日志现象对齐代码异常出口以强化或证伪某条链。**串链内功心法留 M-4 占位。**
5. **候选根因**：逐个给候选根因，每个必含——
   - **证据引用**：坐实的事实带 `log:<行号>` / 报文 / `code_evidence` 锚点；
   - **黑盒验证方法**：外部可执行的复现/验证手段（构造触发条件 → 观测判据）；
   - **置信度**：坐实结论直述；未坐实标 **【推测】+ basis + verify_method**（溯源双轨制，见 `core/shared/溯源铁律.md`）。
   - **候选排序与置信度定级细则留 M-4 占位。**

## 4. 双模式差异

| 环节 | 速度型 | 深度型 |
|---|---|---|
| 日志挖掘 | primary 内联读片段 | primary 只读工具切片并冻结 `log_summary`，必要时形成 worker obligation |
| 落工件 | 不落（不建 `pangea-data/runs/`）| 建 `pangea-data/runs/<任务id>/` + manifest + 证据包写盘 |
| 断点恢复 | 无 | 读 manifest 续跑（architecture §6.2）|
| 传播链联动 | 内联轻量印证（可选）| 以冻结日志锚点创建 `异常传播` obligation，worker fragment 交叉印证 |
| auditor | 不过 | 过（收尾门）|
| 产出 | 内联定位（Markdown）| 完整定位报告 |

> 速度型不创建 worker obligation、不落 `pangea-data/runs/`；候选根因仍须带证据引用、黑盒验证方法和置信度，溯源双轨制不因模式放松。

## 5. 收尾（深度型）

1. **auditor 复核**：Task 派 `auditor`（独立上下文，只审不改）→ `audit_opinion`（溯源/黑盒可执行性/覆盖/格式四组 checks，schema §4.3）。
2. **覆盖审计 PASS** 才完成；FAIL/CONCERNS → 按 `required_actions` 回挖（补日志证据 / 重挖传播链，manifest `audit.rounds` +1）。**回挖 ≤ 2 轮**，超轮带 CONCERNS 出报告、首页标未决项，交用户裁决。
3. **产出**：定位报告落 Markdown（故障时间线 → 异常传播链 → 候选根因清单（各带证据引用+验证方法+置信度）→ **待用户确认**）。速度型产出为内联定位（Markdown），不套模板、不过 auditor。
4. **回填询问**：R-7.4"是否回填知识"（`core/protocols/` / `core/modules/` / 透镜"典型历史缺陷"栏）写入报告末尾**"待用户确认"节**，不在对话内提问（T-6）。

## 6. 场景衔接（供 primary 推荐）

完成后按 architecture §2.1 衔接表推荐下一步：缺陷单撰写（候选根因坐实为产品缺陷）→ MR/问题单分析（修复后回归验证）。
