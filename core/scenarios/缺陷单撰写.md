# 场景作业流程：缺陷单撰写

> 归属族：test-designer ｜ 模式：**速度型** ｜ 输入要求：定位结论（架构 §2.1 能力菜单）
> 上游：[architecture.md](../../docs/architecture.md) §2.1（场景衔接）、§2.2.2（troubleshooter 定位报告）｜ [requirements.md](../../docs/requirements.md) R-7.1（溯源双轨制）、R-7.2、R-7.3
> **核心准绳**：缺陷单是溯源双轨制（R-7.1）落地最严的产出——现象/证据必须带锚点，根因未坐实必须标【推测】+验证方法；复现步骤须黑盒可执行（外部触发 + 外部观测，R-7.2）。

---

## 1. 场景定位

基于已有定位结论（多来自 troubleshooter 的日志定位/失败用例三分类/抓包定位报告），把结论翻成一份规范缺陷单。是"定位已完成 → 落成可提交、可回归的缺陷单"的收口场景，通常为链路终点。

## 2. 输入（前置到 Dispatcher 收集）

- **定位结论**：troubleshooter 的定位报告 / `runs/` 证据包 / 用户粘贴的现象 + 证据。
  - 含现象、证据链（时间线 / 异常传播链 / 报文序列）、候选根因及其置信度；
  - 定位由 troubleshooter 完成，本场景只转写、不重做定位（见第 3 步边界纪律）。
- **模式**：固定速度型（单缺陷单，内联产出，不 fan-out、不落 `runs/`、不过 auditor）。
- **发现场景**：引发缺陷的 `TC-*` 用例编号（若有），供缺陷单 `发现场景` 字段回溯。

## 3. 流程 / 编排

1. **取定位报告 / 证据**：从 troubleshooter 定位报告或 `runs/` 证据包提取三类料，逐类映射到缺陷单字段：
   - **现象原文** → `实际结果`（原文照搬，不改写）；
   - **证据链**（时间线 / 异常传播链 / 报文序列，每条带 `文件:行号` / 日志时间戳 / 报文原文锚点）→ `定位证据`；
   - **候选根因及置信度标注** → `根因分析`（置信度决定坐实/推测，见第 3 步轨道 B）。
   无现成定位报告时，仅据用户粘贴证据撰写，且不得替 troubleshooter 补做根因推断。
2. **按 `core/templates/缺陷单.md` 字段填写**：逐字段填，不擅改团队模板字段（R-7.3）。关键字段填写要点：
   - **缺陷标题**：现象 + 触发条件一句话（如"NVMe/TCP 异常断链后控制器内存不回收"）。
   - **缺陷编号**：`BUG-<模块>-<序号>`，全局唯一、可被回归用例反向引用。
   - **严重级别**：按数据丢失/服务中断/功能受损/轻微分——致命·严重·一般·提示。
   - **发现场景**：引发缺陷的 `TC-*` 用例编号，保证可回溯。
   - **环境信息**：组网 + 软硬件版本 + 配置，给到可复现的最小环境。
   - **复现步骤**：**黑盒可执行、逐条编号的外部操作**（协议构造/CLI/故障注入/压力）。
   - **预期结果 / 实际结果**：均只写外部表现；实际结果带原文锚点。
   - **定位证据 / 根因分析 / 影响范围 / 规避措施**：证据链带锚点、根因守双轨制（见第 3 步）。
3. **溯源双轨制校验（R-7.1，交付前必过）**：
   - **轨道 A 事实带锚点**：`实际结果`/`定位证据` 的每条现象与证据必须带 `文件:行号` 或日志时间戳或报文原文锚点；给不出锚点的描述降级为推测或删去。
   - **轨道 B 推断标推测**：`根因分析` 若根因**未坐实**（无直达 `文件:行号` 支撑），必须写【推测】+ 依据 + **验证方法**（如"仅打异常路径压测复现、正常路径不复现"），严禁把推测写成确定结论。置信度沿用 troubleshooter 标注。
   - **黑盒可执行校验**：`复现步骤` 每步须是黑盒同学真能执行的外部动作，`预期结果`/`实际结果` 只依据外部现象（R-7.2），禁"观察内部变量"式步骤。
4. **输出缺陷单**：内联产出成品缺陷单（Markdown，套 `core/templates/缺陷单.md` 版式）。

> 边界纪律：test-designer 只**转写**定位结论、不新做根因定位——根因坐实是 troubleshooter 的职责。若定位报告本身根因就是【推测】，缺陷单里也须保持【推测】，不得在转写中"升级"为结论。

## 4. 收尾

1. **产出**：成品缺陷单，收口前自查三条硬门：
   - 事实全带锚点（`实际结果`/`定位证据` 每条可回指 `文件:行号` / 日志 / 报文）；
   - 推测根因带【推测】+ 验证方法，未坐实不写成结论；
   - 复现步骤全部黑盒可执行、判据全部外部可观测。
   速度型不过 auditor，但上述溯源双轨制校验为**硬门**，未过不得输出。
2. **回填询问**：R-7.4"是否回填知识"（该缺陷可回填对应透镜的"典型历史缺陷"栏、`modules/` 知识文件）写入缺陷单末尾**"待用户确认"节**，不在对话内提问（Task 子调用未必能多轮对话，T-6）。

## 5. 场景衔接（供 Dispatcher 推荐）

缺陷单撰写是 architecture §2.1 衔接表的**终点场景**，完成后返回能力菜单。后续修复合入后可由 `MR/问题单分析` 做回归验证，或据缺陷编号补建回归用例（反向引用 `BUG-*`）。
