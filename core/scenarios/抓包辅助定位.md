# 场景作业流程：抓包辅助定位

> 执行主体：primary（诊断工作流） ｜ 新编排（非九步继承）｜ 模式：**深度型**（M3 交付）
> 上游：[architecture.md](../../docs/architecture.md) §2.1（能力菜单/衔接表）、§8（深度型时序）｜ [requirements.md](../../docs/requirements.md) R-7.1、R-7.6
> **纪律**：本文为 M3 新编排，编排逻辑可写实。协议报文与候选根因严守溯源双轨制（事实带 `pkt:<序号>` 报文锚点、推断标【推测】+验证方法）；引用协议常量一律"数值+名称"成对。

---

## 1. 场景定位

从抓包报文反向定位故障，并与日志时间线联合印证。回答"报文层面发生了什么 → 协议哪一步异常 → 根因可能在哪、怎么外部验证"。存储协议为主（NVMe/TCP、iSCSI）。是日志定位的报文侧补充与交叉验证。

## 2. 输入（前置到 primary 收集）

- **pcap 文件路径** 或抓包导出文本，由 primary 的已登记只读抓包解析工具能力处理。
- **（可选）配套日志**：若有同期日志，由 primary 的只读日志切片能力冻结，用于报文↔日志时间线对齐。
- **（可选）时钟基准**：抓包主机与被测端的时钟偏差信息，用于校正报文↔日志的对齐误差；缺失时对齐关系一律标【推测】。
- **模式**：固定深度型（报文解析必须冻结工具输出并落工件）；无速度型变体（报文解析不适合内联裸读）。
- **任务 id**：`抓包辅助定位-<对象slug>-<日期>`（规则见 `core/shared/调度规则.md` 三）。
- **（可选）协议/版本**：明确抓包所属协议与版本（NVMe/TCP、iSCSI 等），供 primary 选择已登记的 PDU 解析能力。

## 3. 编排流程

1. **抓包解析（primary 工具能力）**：primary 用已登记的只读解析器处理 pcap 路径或导出文本，冻结工具版本、输入摘要与 `pcap_summary`（schema §4.2a，`artifact_type=pcap_summary`）：
   - `timeline`：按协议解析的报文时序，每条带 `raw_ref: pkt:<序号>`；
   - `key_signals`：异常报文（乱序/重传/非法字段/协议违例/FES 终止/Reject）；
   - `correlations`：与日志时间线的对齐线索【推测】；
   - `raw_excerpts`：关键报文字段/摘要。
2. **（可选并行）日志取证**：若有配套日志，primary 同期生成冻结 `log_summary`，供下一步对齐；不派发未登记角色。
3. **落盘（运行时职责）**：只可用 `runtime/diagnostic_artifacts.py --root <root> --run-id <任务id> --file <json>` 发布；`pcap_summary` 与可选 `log_summary` 的固定路径分别为 `internal/diagnostics/pcap-summary.json`、`internal/diagnostics/log-summary.json`。每个 JSON 严格符合 `schemas/diagnostic-artifact.schema.json`，至少有一条对应 `pkt:<正整数>` / `log:<正整数>` 锚定证据。运行时以 Run 级 flock、dirfd + `O_NOFOLLOW` 和 durable journal 原子推进，索引固定绑定 `input_sha256/body_sha256/content_sha256/state=committed`；恢复必须重放同一绑定，禁止覆盖冲突工件或用聊天摘要代替。
4. **报文时序 ↔ 日志时间线对齐**：以 `pcap_summary.correlations` 为线索，把报文事件（`pkt:<序号>`）与日志事件（`log:<行号>`）按时序对齐，锁定"报文异常点"与"日志异常点"是否同源。对齐关系为推断的标【推测】+ basis。
   - 无配套日志时，本步退化为纯报文侧时序分析，对齐环节跳过，报告注明"仅报文侧定位，未与日志交叉印证"。
5. **协议层异常定位**：在对齐后的时间线上定位握手失败、序列违例、字段非法、异常终止或重传风暴；每条带 `pkt:<序号>` 锚点，协议常量“数值+名称”成对。解析器输出只作证据，不自动升级为根因。
6. **候选根因**：需联动源码时，由运行时把冻结 `pkt:<序号>` 锚点与源码 inventory 绑定成 `异常传播` obligations/ranges，交同一 `analysis-worker` 反向印证代码异常出口。逐个候选必含——
   - **证据引用**：坐实事实带 `pkt:<序号>`（及对齐的 `log:<行号>`）锚点；
   - **黑盒验证方法**：外部可执行的复现/验证手段（构造报文条件 → 观测判据）；
   - **置信度**：坐实结论直述；未坐实标 **【推测】+ basis + verify_method**（溯源双轨制，见 `core/shared/溯源铁律.md`）。

## 4. 协议解析范围与抓包局限（编排注记）

- **解析范围**：已登记工具按存储协议解析 PDU——NVMe/TCP（ICReq/ICResp、Command/Response Capsule、H2CData/C2HData、R2T、C2HTermReq(FES)）、iSCSI（Login、SCSI Command/Response、R2T、Reject、NOP）等。协议外的裸 TCP 层信号（重传/RST/窗口）作为传输侧旁证。
- **局限须在报告标注**：单向抓包 / 抓包点偏移 / 采样丢包 / 加密载荷会导致时序不全——此类情况下候选根因**只能落在【推测】轨**，并注明"需补全对端/全量抓包复验"，不得凭残缺报文坐实结论。
- **与日志的取舍**：报文证据强于日志的场景（协议违例、时序竞态）优先以 `pkt:<序号>` 为锚；日志强于报文的场景（内部状态、资源）回退到日志定位联合判断。
- **落盘边界**：pcap/log 证据包、对齐后的时间线、候选根因均落 `pangea-data/runs/<任务id>/`；报文原文只截关键字段入 `raw_excerpts`，禁止改写，超大 pcap 由 primary 工具按序号区间分片并冻结进度（`status: partial`）。

## 5. 收尾（深度型）

1. **auditor 复核**：Task 派 `auditor` → `audit_opinion`（溯源/黑盒可执行性/覆盖/格式四组 checks，schema §4.3）。重点审：报文锚点齐备、协议常量成对、【推测】配验证方法。
2. **覆盖审计 PASS** 才完成；FAIL/CONCERNS → 按 `required_actions` 回挖（补报文证据 / 重做时间线对齐，manifest `audit.rounds` +1）。回挖 ≤ 2 轮，超轮带 CONCERNS 出报告、首页标未决项，交用户裁决。
3. **产出**：定位报告落 Markdown（报文时序 ↔ 日志对齐 → 协议层异常 → 候选根因清单（各带证据引用+验证方法+置信度）→ **待用户确认**）。
4. **回填询问**：R-7.4"是否回填知识"（`core/protocols/` 协议异常模式 / 透镜"典型历史缺陷"栏）写入报告末尾**"待用户确认"节**，不在对话内提问（T-6）。

## 6. 场景衔接（供 primary 推荐）

完成后按 architecture §2.1 衔接表推荐下一步：日志定位（联合定位、深化时间线）→ 缺陷单撰写（候选根因坐实为产品缺陷）。
