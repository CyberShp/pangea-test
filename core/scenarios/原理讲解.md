# 场景作业流程：原理 / 流程讲解

> 归属族：dev-expert ｜ 新编排（讲解型，非九步继承）｜ 模式：**速度型为主**（复杂主题可升深度型）
> 上游：[architecture.md](../../docs/architecture.md) §8（速度型时序）、§2.2.1（知识优先级 R-7.4）｜ [requirements.md](../../docs/requirements.md) R-7.4、R-8.4
> **纪律**：本场景是讲解型编排，不产出黑盒用例、不过 auditor、**不落 `runs/`**。编排逻辑（知识优先级 → 剧本组织讲解 → 产出 Markdown）为 M1 新搭，可写实；不涉及 Codetalks 内网专属分析话术，无迁移占位。

---

## 1. 场景定位

向黑盒测试同学讲清一段代码流程或一个协议原理（如"NVMe/TCP 一个读命令怎么从收包走到响应""连接状态机怎么迁移"）。目标是**把内部逻辑翻译成外部可观测的行为脉络**，帮同学建立心智模型——是理解型速度场景，不是分析型深度场景，**产出讲解而非用例**。

## 2. 输入（前置到 Dispatcher 收集）

- **讲解主题**（协议名 / 模块名 / 流程名 / 函数名）。
- **源码路径**：按 R-8.4 先询问"是否基于源码分析"（前置在 Dispatcher 完成）——**知识文件命中时可不需要源码**（见 §3 步骤 1）。
- **模式**：默认速度型；主题极复杂、用户要"系统讲透"时可升深度型（走 fan-out + 落 runs，同 §4 说明）。
- **任务 id**：速度型**不生成**（不落 `runs/`）；仅升深度型时按 `core/shared/调度规则.md` 三生成。

## 3. 流程（速度型，内联执行、不落工件）

1. **知识优先级（R-7.4，先知识文件后读码）**：
   - **先读** `core/protocols/`（协议领域知识，经 `_index.md` 查）与 `core/modules/`（模块领域知识，经 `_index.md` 查）——命中则以知识文件为讲解主料，可**免读码**。
   - **无命中则现场读码**：族 agent 内联轻量读码（速度型不走 code-excavator、不落 `runs/`，见 architecture §8 与 R-7.6）。
2. **用剧本"思维骨架"组织讲解**（借剧本的**结构视角**，非派发 excavator）：
   - **流程型主题** → 借 `主干追踪` 视角：入口点 → 主干调用链 → 与外部可观测点（报文/CLI/日志/告警，查 `core/shared/观测手段目录.md`）的接触面，串成一条"从触发到可观测"的线。
   - **状态型主题** → 借 `状态机提取` 视角：状态集合 → 迁移（源态→事件→目标态）→ 外部触发手段与可观测状态映射。
   - **协议型主题** → 借 `协议报文收发路径` 视角（M3 剧本；M1 期间以 `主干追踪` 近似）：收包 → 解析/校验 → 分发 → 发包，标每段的可观测线上行为。
   - 混合主题按需组合上述视角。
3. **溯源仍守铁律**：讲解中引用的具体代码点仍标 `文件:行号`（R-7.1），推断标【推测】；只是不产结构化证据包（速度型内联）。
4. **服务对象校准**：讲解措辞面向黑盒测试同学——内部实现术语一律配一句"外部怎么看/怎么触发"，避免只讲代码不讲可观测面（这是 dev-expert"翻译内部逻辑为外部行为"的人设要求）。

## 双模式差异

| 环节 | 速度型（默认）| 深度型（复杂主题）|
|---|---|---|
| 读料 | 内联读知识/读码，不走 code-excavator | fan-out code-excavator 补全事实 |
| 落盘 | 不落 `runs/` | 中间证据包落 `runs/`（仅为组织讲解）|
| 剧本 | 借剧本"思维骨架"内联组织 | 派发剧本实例回收证据包 |
| 收尾 | 直接产讲解 Markdown | 组织证据为讲解，仍不过 auditor、不产用例 |

> 依据 R-7.6 / architecture §8：讲解型无论速度/深度，产出恒为"流程讲解"，绝不产黑盒用例、不进覆盖审计门——与分析型场景的根本分野。

## 4. 复杂主题升深度型（可选）

主题过大（如"讲透整个 NVMe/TCP target 收发全链路"）时，族 agent 判为深度型：走 §其它深度场景的 fan-out 机制（Task→code-excavator 各注入 `主干追踪`/`状态机提取`/`协议报文收发路径`，证据包落 `runs/<任务id>/`，manifest 登记，断点恢复见 architecture §6.2），把回传证据包**组织为讲解**而非 SFMEA/用例。此路径仍不过 auditor、不产用例——讲解型收尾（§5）不变，只是中间用了深度挖掘补全事实。

## 5. 收尾（讲解型，无 auditor、无用例）

1. **产出流程讲解 Markdown**：结构建议——主题与范围 → 触发入口 → 主流程/状态迁移脉络（配 `文件:行号` 溯源）→ 关键分支与异常路径 → **外部可观测行为对照表**（内部环节 ↔ 测试同学能看到的现象/观测手段）→ 小结。
2. **不落 `runs/`、不过 auditor、不产黑盒用例**（本场景是讲解不是分析）；深度型变体的 `runs/` 工件仅为组织讲解的中间料，不进收尾门。
3. **回填询问**：R-7.4"是否把本次梳理沉淀为 `protocols/`/`modules/` 知识文件"——写入讲解末尾"待用户确认"节，不在对话内提问（T-6）。
