# 场景作业流程：失败用例三分类

> 归属族：troubleshooter ｜ 新编排（非九步继承）｜ 模式：**深度型**
> 上游：[architecture.md](../../docs/architecture.md) §2.1（能力菜单/衔接表）、§8（深度型时序）｜ [requirements.md](../../docs/requirements.md) R-7.1、R-7.6
> **纪律**：本文为 M2 新编排，编排逻辑可写实。三分类判据均为**外部证据判据**，甄别结论严守溯源双轨制（事实带日志锚点、推断标【推测】+验证方法）。

---

## 1. 场景定位

对一条（或一批）失败用例做归因三分类——判定失败到底是**产品缺陷 / 用例缺陷 / 环境问题**，并给各类判据与证据链、导出后续动作。回答"这个用例挂了，是谁的锅、下一步找谁"。

## 2. 输入（前置到 Dispatcher 收集）

- **失败用例**：用例正文（预期结果 / 实际结果 / 复现步骤）+ 失败现象描述。
- **日志**：用例执行期日志片段或路径（交 log-miner 取证）。
- **模式**：固定深度型（归因需证据链，走 log-miner + 落工件）。
- **（可选）规格锚点**：用例所依据的规格/设计条目或 `core/modules/` 知识文件，用于判定"系统行为是否违反规格"（产品缺陷 vs 用例缺陷的分界）。
- **任务 id**：`失败用例三分类-<对象slug>-<日期>`（规则见 `core/shared/调度规则.md` 三）。

## 3. 编排流程

1. **日志取证（经 log-miner）**：Task 派 `log-miner`（输入执行期日志片段或路径）→ 产出 `log_summary`（schema §4.2a，`timeline`/`key_signals` 每条带 `raw_ref: log:<行号>`）。
2. **落盘（职责归族 agent）**：log-miner 只读回传、写不了盘；族 agent 建 `runs/<任务id>/`、维护 `manifest.md`、把 `log_summary` 写盘（`失败用例三分类-<对象slug>-log_summary-<序号>.md`）。断点恢复读 manifest；目录已存在先问用户"续跑还是重挖"。
3. **对齐用例期望**：把 `log_summary.timeline` 与用例"预期结果 vs 实际结果"对齐——定位**失败发生点**（哪一步、哪个信号偏离预期），带 `log:<行号>` 锚点。
   - **偶发/不可复现**：日志无稳定异常信号、失败仅偶现时，先归入"待定"，建议补齐复现条件或多轮采样，不在证据不足时强判三类之一。
4. **三类判据逐一甄别**（对每条判据给证据；给不出锚点的降为【推测】+验证方法）：

   | 归因类 | 判据（外部证据）| 证据链 |
   |---|---|---|
   | **产品缺陷** | 环境正常、用例正确，被测系统实际行为违反规格/设计（错误码、异常报文、数据不一致、崩溃/泄漏）| 日志异常信号 + 违反的规格条目；可联动 dev-expert `异常传播` `code_evidence` 印证代码异常出口 |
   | **用例缺陷** | 系统行为符合规格，但用例预期写错 / 步骤缺前置 / 断言过严或过松 / 时序竞态未等待 | 日志显示系统按规格执行 + 用例预期与规格的偏差点 |
   | **环境问题** | 失败源于组网/依赖/配置/资源/工具，与被测逻辑无关（端口不通、盘符缺失、版本不匹配、磁盘满、时钟漂移）| 日志中的环境类信号（连接拒绝/超时/资源耗尽/依赖缺失）+ 复现仅在特定环境 |

   > 甄别纪律：三类**互斥判定优先级**——先排除环境问题（环境不干净则其余结论不可信），再区分产品缺陷 vs 用例缺陷（核心是"系统行为是否违反规格"）。判定不唯一时并列列出候选类，各标置信度，交用户裁决。
   > 每条判据的"命中/不命中"都要落到具体日志信号（带 `log:<行号>`）；仅凭现象推断而无锚点的判定降级为【推测】并配验证方法，禁止无证据下确定性归因。

5. **按类导出动作**：
   - **产品缺陷类** → 转缺陷单：按 `core/templates/缺陷单.md` 起草（现象/复现步骤/定位证据引 `runs/` 证据包/根因分析守双轨制）。
   - **用例缺陷类** → 转用例评审：给出用例需修正点（预期/步骤/断言/等待），移交 test-designer `用例评审` 场景。
   - **环境问题类** → 给环境修复建议：列出需修复的环境项 + 外部可执行的核对/修复步骤（如"核对目标端口连通性 → 修正组网 → 重跑用例复验"）。
   - **可回溯性**：每类结论均绑定失败用例的**用例编号**（`TC-*`），转出的缺陷单 `发现场景` / 用例评审 `待修正项` 反向引用该编号，保证归因链闭合可审计（R-7.1）。

6. **混合归因与灰区**：一次失败可能叠加多类成因（如环境抖动诱发产品缺陷暴露）。此时**主因 + 次因**分列，各带独立证据链与置信度；主因不可判定时并列候选、交用户裁决，不强行收敛到单一类。批量用例逐条独立三分类后再汇总归因分布，避免一条结论外推整批。

## 4. 收尾（深度型）

1. **auditor 复核**：Task 派 `auditor` → `audit_opinion`（溯源/黑盒可执行性/覆盖/格式四组 checks，schema §4.3）。重点审：每条归因是否带证据锚点、【推测】是否配验证方法。
2. **覆盖审计 PASS** 才完成；FAIL/CONCERNS → 按 `required_actions` 回挖（补日志证据 / 重判归因，manifest `audit.rounds` +1）。回挖 ≤ 2 轮，超轮带 CONCERNS 出报告、首页标未决项，交用户裁决。
3. **产出**：分类报告落 Markdown（失败发生点 → 三类判据甄别表 → 各类归因结论（带证据链+置信度）→ 导出动作 → **待用户确认**）。批量用例逐条给分类，汇总分布。
4. **回填询问**：R-7.4"是否回填知识"（环境类共性问题 / 透镜"典型历史缺陷"栏）写入报告末尾**"待用户确认"节**，不在对话内提问（T-6）。

## 5. 场景衔接（供 Dispatcher 推荐）

完成后按 architecture §2.1 衔接表推荐下一步：缺陷单撰写（产品缺陷类）/ 用例评审（用例缺陷类）；环境问题类修复后回归复验。
