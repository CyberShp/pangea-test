# 场景作业流程：可测试性分析

> 执行主体：primary（测试设计工作流） ｜ 模式：**深度型** ｜ 输入要求：源码/设计（架构 §2.1 能力菜单）
> 上游：[architecture.md](../../docs/architecture.md) §2.1（场景衔接）、§6（obligation/range 分片并发 + 断点恢复）｜ [requirements.md](../../docs/requirements.md) R-7.2、R-6.1、R-8.4
> **核心准绳**：primary 测试设计阶段的一切结论落到"**外部能否触发 + 外部能否观测**"。本场景专门审视一个模块/特性在黑盒视角下有多少行为够得着——触发得到、观测得出，禁以内部变量充当触发面/观测面。

---

## 1. 场景定位

对一个模块/特性做黑盒**可测试性**评估：逐个待测行为判定"外部能不能触发它、外部能不能看见它的结果"，标出黑盒盲区（能发生但外部无差异、无接口可观测的行为），并给出可测试性改进建议（增加可观测点/CLI/日志/错误码）。产出**可测试性报告**，是"要不要/能不能测得动"的前置判断，通常喂给 `测试策略` 与 `模块全量分析`。

## 2. 输入（前置到 primary 收集）

- **分析对象**：模块/特性名 + 源码路径。
  - 按 R-8.4，**先询问用户"是否基于源码分析"**，是则索要路径；
  - 仅有设计文档时按设计接口面评估、结构证据项标"缺源码佐证"。
- **模式**：固定深度型（需结构证据支撑触发/观测判定）。
- **任务 id**：`可测试性分析-<对象slug>-<日期>`（规则见 `core/shared/调度规则.md` 三；自举时primary 同规则自生成）。

## 3. 流程 / 编排

1. **取结构证据（必要时 obligation/range 分片并发 analysis-worker）**：可测试性判定要以真实控制结构为据，而非凭空。运行时按对象建立 immutable obligation/range context packs，并发调用同一只读 `analysis-worker`，各包分别绑定：
   - `分支枚举`——枚举全部分支，供后续逐分支判"外部可否触发/可否观测"；
   - `异常传播`——异常产生/传播/处置路径，异常路径最易成盲区；
   - 视对象追加 `状态机提取`（有状态机）/ `资源生命周期`（有资源申请释放）。
   worker 只返回 strict fragment；运行时校验 obligation/range/receipt 后，由 primary 持久化通过校验的证据与模型贡献：
   - 运行时创建 `pangea-data/runs/<任务id>/`、维护 `manifest.md`，并将通过 obligation/range/receipt 校验的 `analysis_fragment` 及其完整模型贡献按 schema（`core/shared/证据包schema.md`）写盘；primary 只消费固定工件；
   - 断点恢复读 `pangea-data/runs/<任务id>/manifest.md` 续跑（architecture §6.2）；目录已存在时先问用户"续跑还是重挖"。
2. **逐点评估"外部能否触发 + 外部能否观测"**：以证据包每个分支/状态迁移/异常出口为一个"待测行为点"，两栏判定：
   - **外部可触发性**：是否存在协议报文构造 / CLI 命令 / 故障注入 / 压力施加 / 配置变更等外部手段把系统逼到该点。存储域示例——某异常分支需靠"注入 TCP RST / `iptables` DROP 制造静默断链"才进得去，进不去即"触发盲区"。
   - **外部可观测性**：该点发生后是否在 `core/shared/观测手段目录.md` 的类别（协议报文 / CLI 回显 / 告警 / 日志 / 性能统计 / 错误码）里留下可区分的外部差异。存储域示例——内存是否泄漏可经"阵列侧内存统计 + 水位告警"观测；若某失效只改内部计数、外部无任何统计/告警反映，即"观测盲区"。
3. **标出黑盒盲区**：把无外部差异的点汇成盲区清单，逐条带 `文件:行号` 锚点（R-7.1）。两类死角优先引证据包：
   - **异常传播盲区**：多条异常出口回同一个泛化错误码 / 静默返回，外部无法区分是哪条路径失效（引 `异常传播` 证据包的"无外部差异"项）；
   - **分支枚举盲区**：两分支走不同内部逻辑却外部表现相同，黑盒无法判定进了哪支（引 `分支枚举` 证据包的"无外部差异"项）。
   这些是黑盒既测不动、auditor 也审计不出覆盖的点，须显式登记而非略过。
4. **给可测试性改进建议**：对每个盲区提"要外部够得着，需增加什么"，形成盲区→改进闭环：
   - **增可观测点**：区分性错误码 / 状态回显 CLI / 关键路径日志埋点 / 性能统计计数器；
   - **增可触发钩子**：故障注入开关 / 调试通道 / 配置项，把够不着的点逼得出来；
   - 每条建议须说明"补了它，哪条无外部差异项就能判 PASS/FAIL"，让改进可验收。

> 触发/观测两栏禁止以内部变量凑数：`内部状态==X`、`引用计数 refcnt` 不是合法观测面；若某点只能靠读内部变量判定，它就是观测盲区，须进盲区清单而非记作"可观测"。

## 4. 收尾门

1. **auditor 复核**：Task 派 `auditor`（独立上下文，只审不改）→ `audit_opinion`（溯源/黑盒可执行性/覆盖/格式四组 checks，见 `core/shared/证据包schema.md`）。本场景重点是**黑盒可执行性**组——盲区判定是否严守"外部触发+外部观测"、有无把内部变量误记为观测面。
2. **PASS 才完成**；FAIL/CONCERNS → 按 `required_actions` 回挖对应剧本（≤ 2 轮）。
   - 回挖仍不过则带 CONCERNS 出报告、首页标未决项，交用户裁决。
3. **产出**：可测试性报告，章节骨架——
   分析对象 → 待测行为点清单（每点带外部触发性 / 外部观测性两栏判定）→ **黑盒盲区清单**（带 `文件:行号` 锚点）→ **可测试性改进建议**（盲区 → 需增观测/触发点）→ **待用户确认**。
4. **回填询问**：R-7.4"是否回填知识"（盲区模式可沉淀入 `core/shared/观测手段目录.md` 或 `modules/`）写入报告末尾**"待用户确认"节**，不在对话内提问（Task 子调用未必能多轮对话，T-6）。

## 5. 场景衔接（供 primary 推荐）

完成后推荐下一步（architecture §2.1 衔接表）：**测试策略**（把可测的面转成分层策略）→ **模块全量分析**（对可测面做全量推导）。盲区较多时，改进建议可先反馈给开发再回测。
