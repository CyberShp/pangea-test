# 单点故障透镜（DFX 维度：可用性）

> 一句话：找"一处坏了全盘停"——某个组件/路径/资源没有冗余或冗余形同虚设，它的故障直接中断对外服务；或号称双份实则共命运（同源、同锁、同队列、切换不生效）。

## 风险机理

存储阵列的可用性承诺（如 99.999%）建立在"任一单点故障都有旁路"之上。单点故障透镜找的是"冗余承诺的漏洞"：要么根本没冗余，要么冗余在关键处失效。典型成因：
- **无冗余路径**：数据/控制路径只有一条，某链路/控制器/进程故障即全断（无多路径、无双控接管）。
- **伪冗余（共命运）**：两条路径共享同一底层资源（同一把锁、同一队列、同一内存池、同一时钟/配置源），单点故障同时打翻两份。
- **切换不生效**：有备份但故障检测缺失/超时过长/切换逻辑有 bug，故障发生时切换不触发或切换失败。
- **控制面单点**：管理/心跳/仲裁进程单实例，其故障导致整个集群失去协调（脑裂或全停）。
- **单点在初始化/配置**：单一配置源、单一元数据副本、单一注册表，损坏即全局不可用。
- **容量单点**：单一资源池被所有业务共享，一路耗尽拖垮全部（与 `过载保护` 相邻）。

## 代码特征模式（给 excavator 的扫描指引）

以下为风险扫描剧本对本对象的 grep/阅读指令，命中即记 `文件:行号` + 机理：
- **冗余/切换机制**：`failover|takeover|standby|active.?active|active.?passive|multipath|mpath|redundan|heartbeat|quorum|arbitration|witness`。逐一回答"有几份、如何检测故障、如何切换、切换失败怎么办"。
- **共享底层资源**：多路径/多实例是否共用同一 `lock|mutex|list|pool|workqueue|kthread|全局单例`——共享点即伪冗余嫌疑。
- **单例结构**：`static .* = ` 全局单实例、`singleton`、唯一 fd/socket/连接承载全部业务；其故障域即单点。
- **故障检测**：心跳/探活的周期与超时（`timeout|keepalive|heartbeat_interval`）是否合理；检测缺失则切换永不触发。
- **切换幂等与竞态**：切换/接管路径是否处理"切换中再故障""双方都认为自己是主"（脑裂）。
- **控制面实例数**：管理/仲裁/元数据服务是单实例还是多副本；单副本即控制面单点。
- **免疫判断**：若对象本就设计为无状态可重建、或位于已被上层冗余覆盖的路径，则给"免疫理由"。

## 典型历史缺陷

<!-- 团队回填：历史缺陷案例 -->
- （通用示意）双控制器 HA 号称 active-active，但两控的元数据更新共用同一把全局锁的持有者进程，该进程 hang 导致两控同时卡死，冗余形同虚设。
- （通用示意）多路径下发共享同一个 workqueue，某一路径的阻塞占满队列，另一"冗余"路径的 IO 也被拖住，单路径故障演变为全路径不可用。

## 黑盒触发手段

存储领域从外部逼出单点的手段：
- **逐组件故障注入**：依次拔某条链路、复位某个控制器、kill 某个进程，验证业务是否经旁路继续（IO 不中断或秒级恢复）。
- **HA 切换演练**：主控故障触发切换，测量切换时间与 IO 中断窗口，验证切换真实生效。
- **共命运探测**：同时对"两份冗余"施压/施故障，观察是否一同倒下（暴露共享底层资源）。
- **控制面故障**：故障仲裁/心跳/管理进程，验证是否脑裂或全局失能。
- **链路多路径切换**：断多路径中的一条，验证 IO 自动切到另一条。

## 观测判据（从 `core/shared/观测手段目录.md` 选手段）

判 PASS/FAIL 的外部现象：
- **数据面读回校验（第七类）+ 性能统计**：注入单点故障后主机 IO 应持续（或在承诺窗口内恢复），IOPS/带宽不应归零；业务全断 = FAIL。
- **CLI 回显**：故障后应显示旁路/备份已接管（路径状态、主备角色切换）；显示无可用路径/未切换 = FAIL。
- **告警**：单组件故障应产生对应告警且业务级"服务中断"告警**不应**出现（说明被冗余吸收）；出现服务中断告警即单点暴露。
- **性能统计**：切换窗口内时延尖峰应在承诺范围内、随后回稳；长时间不恢复 = FAIL。
- **协议报文/错误码**：故障期间主机侧至多见短暂重试/路径切换，不应收到持续 IO 失败错误码。

## 用例骨架

> 格式见 `core/templates/黑盒用例.md`（字段：用例编号/用例名称/预置条件/外部触发手段/操作步骤/观测手段/观测判据/推导方法论/覆盖目标/关联风险）。

- **用例雏形 1｜控制器故障业务不中断**：预置双控 HA + 持续 IO → 外部触发：复位一个控制器 → 观测手段：性能统计（IOPS 连续性）+ CLI 主备角色 + 告警 → 判据：IO 在承诺窗口内不中断、备控接管、无服务中断告警；业务全断判 FAIL。推导方法论：端到端场景（M3 待补；过渡期按 `_selector` 规则回退种子方法并标注）。关联风险：本透镜、恢复路径。
- **用例雏形 2｜冗余非共命运**：预置双冗余路径 + IO → 外部触发：仅对其中一路径注入阻塞/故障 → 观测手段：另一路径性能统计 + CLI 路径状态 → 判据：另一路径 IO 不受影响；两路径同时劣化说明存在共享底层资源，判 FAIL。推导方法论：错误推测。关联风险：本透镜。
