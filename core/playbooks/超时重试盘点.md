# 超时重试盘点（P8）

> 本剧本挖"等多久、试几次、然后干嘛"：盘点对象内所有超时/重试/退避机制、它们的参数来源（硬编码/配置/协商），以及超时触发后的动作与外部可观测现象——存储链路超时恢复的高发缺陷区。

## 目标

给定挖掘对象，产出：
- 所有**超时点**（定时器、超时阈值），及其时长来源与触发后动作；
- 所有**重试点**（重试计数、退避策略），及其上限与耗尽后行为；
- 每个超时/重试关联的外部可观测现象（复位、错误码、告警、重传）。

不做机理风险判定（交 `风险扫描` 透镜=超时恢复）；本剧本只做"客观清点"，把散落的时间常量与重试逻辑收成一张表。

## 步骤

（步骤号与证据包 `progress.done_steps` 对应）

1. **找超时/定时器**：grep 定时器与超时特征：
   - `timer_setup`/`mod_timer`/`schedule_delayed_work`/`queue_delayed_work`；
   - `*_timeout`、`jiffies + ...`、`msecs_to_jiffies(...)`、`ktime`/`hrtimer`；
   - 轮询等待 `wait_event_timeout`/`schedule_timeout`。
   逐个记 `位置` 与超时对象。
2. **溯参数来源**：对每个超时时长，判定来源——**硬编码常量**（`#define ... TIMEOUT`）/ **配置项**（module_param、configfs 属性、sysfs）/ **协议协商**（如 NVMe kato Keep-Alive Timeout、iSCSI 登录协商参数）。协议常量成对写"数值+名称"，入 `timeouts[]`。
3. **找重试/退避**：grep `retry`/`retries`/`max_retries`/`nr_retries`、循环重试计数、退避 `backoff`/指数退避。记重试上限、退避策略、耗尽后行为（放弃/断链/上报），入 `retries[]`。
4. **标可观测现象**：对每个超时/重试，标其触发后外部能看到什么（连接复位、发 NVMe/TCP C2HTermReq、错误码返回、告警日志、报文重传），并入对应条目；无法确定触发条件的标【推测】入 `inferences[]`。

## 证据包字段

（字段名对齐 architecture §3 P8："timeouts[]{位置,时长来源,触发动作,可观测现象} / retries[]{位置,次数,退避策略,上限行为}"）

```yaml
findings:
  timeouts:                      # 超时点清单
    - 位置: <文件:行号>
      时长来源: <硬编码(值+宏名) | 配置(项名) | 协商(协议参数名)>
      触发动作: <超时后做什么，如 断链并释放队列>
      可观测现象: <外部能看到什么，如 连接复位、发 C2HTermReq PDU>
  retries:                       # 重试点清单
    - 位置: <文件:行号>
      次数: <重试上限，带宏名/来源>
      退避策略: <固定间隔 | 指数退避 | 无退避>
      上限行为: <耗尽后做什么，如 放弃并上报 EIO>
```

> 溯源纪律：`findings` 每条必带 `位置: 文件:行号`。协议超时/重试常量必须成对写"数值 + 名称"（如 `KATO=默认无(0) Keep-Alive Timeout`、`FES=3h Header Digest Error`），不得只写裸数值。触发条件不确定处标【推测】入 `inferences[]` 给黑盒验证方法。

## 存储领域示例

> **说明：本节行号为示意虚构，非真实代码锚点，仅示范字段填法。**

对象 `nvmet_tcp` 连接保活与收包超时：

```yaml
findings:
  timeouts:
    - 位置: drivers/nvme/target/core.c:412
      时长来源: 协商 KATO=host 下发值 Keep-Alive Timeout（NVMe Connect 命令协商）
      触发动作: 保活超时 nvmet_ctrl_fatal_error 置控制器 fatal、拆链
      可观测现象: 主机侧连接断开、target 侧 pr_err 保活超时日志、CLI 显示 ctrl 掉线
    - 位置: drivers/nvme/target/tcp.c:1305
      时长来源: 硬编码 NVMET_TCP_RECV_BUDGET(8) 收包预算轮次（非时间超时，让出 CPU）
      触发动作: 达预算让出 io_work、重新入队
      可观测现象: 无直接外部现象（内部调度公平性）
  retries:
    - 位置: drivers/nvme/target/tcp.c:660
      次数: 无显式上限（发送 EAGAIN 时循环重试直至 socket 可写）
      退避策略: 无退避，依赖 sk_write_space 回调重驱动
      上限行为: socket 持续不可写则积压，最终随连接超时被上层拆链
inferences:
  - claim: 【推测】发送侧 EAGAIN 无重试上限，对端长期不收可能导致响应无限积压
    basis: :660 循环依赖 write_space 回调，未见发送侧独立超时护栏
    verify_method: 主机侧建链后停止接收（TCP 零窗口），观测 target 响应队列是否无限增长、多久才由保活超时兜底拆链
```

## 与黑盒观测的接触面

超时/重试参数深埋代码，黑盒同学难以从外部得知具体阈值；本剧本把它们清点成表，直接服务黑盒的"时间维度用例"：
- 每个 `timeouts` 条目给出"等多久触发 + 触发后外部现象"，primary 据此设计**超时边界用例**（略小于/略大于阈值，观测现象是否如期），`时长来源` 告诉黑盒"这个阈值能否从外部配置/协商改变"，决定用例是否需先设参数；
- 每个 `retries` 条目的 `次数`/`上限行为` 是**重试耗尽用例**的判据——制造持续失败，验证是否在预期次数后按预期上报/断链；
- 协议超时（KATO、iSCSI 登录超时等）成对记的"数值+名称"让 primary 能直接引用协议规格设计协商类用例；不确定的触发条件经 `verify_method` 转成黑盒验证动作，不硬写结论。
