# 调用链影响域（P6）

> 本剧本挖"改这里会牵动谁"：给定一个改动点/函数，反向算出上游调用者、正向算出下游被影响面与共享数据波及，归纳出受影响的外部可观测特性——服务于回归影响分析（MR 分析高频）。

## 目标

给定一个目标符号（被改动的函数/变量/结构体成员），产出：
- 谁会调到它（反向 caller 树）；
- 它会调到谁、以及经共享数据间接影响谁（正向 callee + 共享状态波及）；
- 归纳出这些影响最终落到哪些**外部可观测特性**上，供 primary 圈定回归测试范围。

不做风险判定（交 `风险扫描`），不追完整状态机（交 `状态机提取`）；本剧本只画"改动的涟漪半径"。

## 步骤

（步骤号与证据包 `progress.done_steps` 对应）

1. **定位目标符号**：按 MR/用户给定的改动点 grep 出符号定义处，记 `target` 的 `位置: 文件:行号` 与类型（函数/宏/结构成员/全局变量）。
2. **反向找 caller**：grep 符号被调用处（`<符号>(`、赋给函数指针 `.xxx = <符号>`、宏展开点），逐层向上追 caller 树。存储底软特征：注意函数指针注册点（`ops` 表、`.complete`/`.done` 回调）会**切断静态 caller 链**，此类间接调用者标【推测】入 `inferences[]`。每个 caller 记 `位置`。
3. **正向找 callee 与共享数据波及**：① 追目标函数体内直接调用的下游函数入 `callees[]`；② 找它读写的共享数据（全局/结构成员/引用计数），凡"写"的数据，再 grep 谁"读"该数据——这些读者是间接影响面，入 `shared_state_impact[]`。
4. **归纳外部特性**：把 caller/callee/共享数据波及沿链走到外部可观测点（报文类型、CLI 字段、统计计数、错误码），归纳"改动可能改变的外部行为"入 `affected_external_features[]`，作为回归范围。

## 证据包字段

（字段名对齐 architecture §3 P6："target / callers[] / callees[] / shared_state_impact[] / affected_external_features[]"）

```yaml
findings:
  target:                        # 改动点符号
    符号: <目标符号，如 nvmet_tcp_queue_response>
    位置: <文件:行号>
    类型: <函数 | 宏 | 结构成员 | 全局变量>
  callers:                       # 反向调用者（谁会调到 target）
    - 符号: <caller 符号>
      位置: <文件:行号>
      调用方式: <直接调用 | 函数指针注册 | 宏展开>
  callees:                       # 正向被调（target 调到谁）
    - 符号: <callee 符号>
      位置: <文件:行号>
  shared_state_impact:           # 经共享数据的间接影响面
    - 数据: <共享数据名，如 queue->nr_cmds>
      写入位置: <文件:行号>
      读取方: <谁读该数据 + 位置>
  affected_external_features:    # 归纳出的受影响外部特性（回归范围）
    - 特性: <外部可观测特性，如 R2T 下发时机>
      关联位置: <文件:行号>
      影响说明: <改动如何可能改变该特性>
```

> 溯源纪律：`findings` 每条必带 `位置: 文件:行号`；函数指针实际指向、宏间接调用者等无法静态确定的关系，标【推测】移到 `inferences[]` 并给黑盒验证方法。

## 存储领域示例

> **说明：本节行号为示意虚构，非真实代码锚点，仅示范字段填法。**

改动点 `nvmet_tcp_queue_response`（NVMe/TCP target 响应入队函数）：

```yaml
findings:
  target: { 符号: nvmet_tcp_queue_response, 位置: drivers/nvme/target/tcp.c:520, 类型: 函数 }
  callers:
    - { 符号: nvmet_req_complete, 位置: drivers/nvme/target/core.c:748, 调用方式: 函数指针注册 }
  callees:
    - { 符号: nvmet_tcp_setup_response_pdu, 位置: drivers/nvme/target/tcp.c:480 }
  shared_state_impact:
    - 数据: queue->resp_list
      写入位置: drivers/nvme/target/tcp.c:534
      读取方: nvmet_tcp_io_work 发送循环 drivers/nvme/target/tcp.c:1230
  affected_external_features:
    - 特性: 响应 PDU（C2HData/RspCapsule）下发顺序
      关联位置: drivers/nvme/target/tcp.c:1230
      影响说明: 入队顺序变化可能改变主机侧收到响应的先后，影响乱序/时延观测
inferences:
  - claim: 【推测】nvmet_req_complete 经 .queue_response 函数指针间接调到 target，静态链在 ops 表处断开
    basis: core.c:748 调用 req->ops->queue_response，ops 在建链时赋值，非直接调用
    verify_method: 下发一条读命令，抓包确认响应 PDU 确由本函数路径构造下发（对比字段特征）
```

## 与黑盒观测的接触面

调用链本身是内部事实，黑盒同学看不到 caller/callee 树；本剧本对黑盒的价值在收敛"回归测试范围"：
- `affected_external_features` 即**回归验证清单**——primary 据此只回归受涟漪波及的外部特性，避免全量重测，也避免漏测；
- `shared_state_impact` 提示"看似无关的功能可能因共享数据被殃及"，是黑盒最易漏测的隐蔽回归面，primary 据此补触发这些读者的用例；
- `inferences[].verify_method` 把"函数指针实际指向"这类静态挖不动的关系，转成"抓包/看回显确认路径"的黑盒验证动作，闭合溯源。
