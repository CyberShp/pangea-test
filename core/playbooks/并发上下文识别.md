# 并发上下文识别（P7）

> 本剧本挖"谁和谁在抢"：识别对象涉及的执行流（中断/软中断/内核线程/工作队列/用户态）、它们共享的数据、保护数据的锁边界，以及疑似无锁竞争点——存储底软并发密集，这是并发缺陷的地图。

## 目标

给定挖掘对象，产出：
- 它涉及的所有**执行流上下文**（谁在跑这段码）；
- 被多个上下文访问的**共享数据**及其保护锁；
- **锁边界/临界区**（哪段码在锁内）；
- **疑似竞争点**（共享数据的无锁访问、锁粒度可疑处）。

不判定竞争是否真会触发失效（交 `风险扫描` 透镜=并发 做机理判定）；本剧本只画"并发地形图"，客观标出共享面与锁边界。

## 步骤

（步骤号与证据包 `progress.done_steps` 对应）

1. **列执行流**：识别对象代码运行在哪些上下文。存储底软常见特征：
   - 中断/软中断：`irqreturn_t` 处理函数、`tasklet`、`napi_poll`、`.data_ready`/`.write_space` sk 回调（软中断上下文）；
   - 内核线程/工作队列：`INIT_WORK`/`queue_work`、`kthread_run`、`.io_work`；
   - 用户态：`ioctl`/configfs `store`/`sysfs` 回调。
   逐个入 `execution_contexts[]`，标 `位置` 与上下文类型（原子/可睡眠）。
2. **列共享数据 + 保护锁**：找被 ≥2 个上下文访问的数据（队列结构成员、链表、引用计数、状态变量），对每项定位其保护锁（`spin_lock`/`mutex`/`rcu`/`atomic`），记 `{数据, 保护锁, 访问上下文}` 入 `shared_data[]`。
3. **标锁边界**：定位每把锁的 `lock`/`unlock` 配对处，记临界区覆盖范围入 `lock_boundaries[]`（锁类型 + 加锁位置 + 解锁位置 + 临界区保护对象）。
4. **标疑似竞争**：客观标出——共享数据未在任何锁下访问、同一数据不同上下文用不同锁、持自旋锁却调可能睡眠函数、check 与 use 之间锁被释放（TOCTOU）——入 `suspected_races[]`，全部标【推测】并入 `inferences[]` 给黑盒验证方法。

## 证据包字段

（字段名对齐 architecture §3 P7："execution_contexts[] / shared_data[] / lock_boundaries[] / suspected_races[]【推测】"）

```yaml
findings:
  execution_contexts:            # 执行流上下文
    - 上下文: <如 软中断(sk_data_ready) | 工作队列(io_work) | 用户态(configfs)>
      位置: <文件:行号>
      属性: <原子/不可睡眠 | 可睡眠>
  shared_data:                   # 共享数据及其保护
    - 数据: <共享数据名，如 queue->cmds 链表>
      保护锁: <锁名/类型，如 queue->state_lock(spinlock) | 无【疑似】>
      访问上下文: [<哪些执行流会访问它>]
  lock_boundaries:               # 锁边界/临界区
    - 锁: <锁名，如 nvmet_tcp_queue->state_lock>
      锁类型: <spinlock | mutex | rcu | ...>
      加锁位置: <文件:行号>
      解锁位置: <文件:行号>
      临界区保护: <这段临界区保护什么>
  suspected_races:               # 疑似竞争点（全部【推测】，同步入 inferences[]）
    - 位置: <文件:行号>
      现象: <如 状态变量在 io_work 无锁读、在 data_ready 有锁写>
      竞争类型: <无锁共享 | 锁不一致 | 持锁睡眠 | TOCTOU>
```

> 溯源纪律：`execution_contexts/shared_data/lock_boundaries` 为可定位事实，每条带 `位置: 文件:行号`；`suspected_races` 属推断，逐条镜像到 `inferences[]` 标【推测】并给黑盒验证方法。

## 存储领域示例

> **说明：本节行号为示意虚构，非真实代码锚点，仅示范字段填法。**

对象 `nvmet_tcp_queue`（NVMe/TCP target 连接队列并发面）：

```yaml
findings:
  execution_contexts:
    - { 上下文: 软中断 sk_data_ready 回调, 位置: drivers/nvme/target/tcp.c:1642, 属性: 原子/不可睡眠 }
    - { 上下文: 工作队列 nvmet_tcp_io_work, 位置: drivers/nvme/target/tcp.c:1203, 属性: 可睡眠 }
  shared_data:
    - 数据: queue->rcv_state
      保护锁: 无【疑似】
      访问上下文: [sk_data_ready 回调, io_work]
  lock_boundaries:
    - 锁: queue->state_lock
      锁类型: spinlock
      加锁位置: drivers/nvme/target/tcp.c:1350
      解锁位置: drivers/nvme/target/tcp.c:1372
      临界区保护: queue->state 连接状态迁移（建链/断链竞争）
  suspected_races:
    - 位置: drivers/nvme/target/tcp.c:1290
      现象: rcv_state 在 io_work 无锁读写，data_ready 回调也可能触发状态推进
      竞争类型: 无锁共享
inferences:
  - claim: 【推测】queue->rcv_state 在软中断与工作队列间无锁共享，高并发建链下可能状态错乱
    basis: :1290 读写 rcv_state 未见 state_lock 保护，而状态迁移路径 :1350 有锁
    verify_method: 多客户端并发反复建链/断链压测，观测是否偶发连接卡死、CLI 显示连接状态异常或 target 侧告警
```

## 与黑盒观测的接触面

并发地形是纯内部事实，黑盒完全看不到锁与上下文；本剧本的价值在为"并发类黑盒用例"提供施压靶点：
- `suspected_races` 的每个竞争点是 primary 设计**并发压力用例**的靶心——`inferences[].verify_method` 给出"用什么并发外部操作（多客户端并发建链/IO/断链）能撞出该竞争"以及"撞出后外部看到什么"（卡死/复位/计数错乱/告警）；
- `execution_contexts` 帮 primary 判断"哪些外部事件会并发驱动同一段码"（如收包软中断 vs 配置下发），据此构造交叠时序用例；
- 本剧本只交并发事实，不下"必然出 bug"结论——竞争是否成灾交 `风险扫描` 透镜=并发 判机理、交黑盒压测证实。
