# 协议报文收发路径（P9）

> 本剧本挖"一个报文的一生"：从 socket 收包到业务处理、再到响应发出的全链路（NVMe/TCP、iSCSI 等），追出收包点→PDU 解析/字段校验→业务分发→发包构造，并标出每段的异常报文处理与线上可观测点——存储协议特色剧本。

## 目标

给定挖掘对象（某协议的收发处理路径），产出：
- **收包路径**（socket recv / DMA / 队列取包）；
- **解析步骤**（PDU 头/胶囊解析、CmdSN/长度/Digest 等字段校验）；
- **业务分发**（按报文类型/opcode 派发到处理函数）；
- **发包路径**（响应/请求 PDU 构造与下发）；
- **畸形报文处理** 与 **线上可观测行为**（回什么 PDU、复位、Term 请求）。

## 步骤

（步骤号与证据包 `progress.done_steps` 对应）

1. **定位收包点**：grep socket 收包与取包特征：`sock_recvmsg`/`kernel_recvmsg`/`.read_sock`/`sk_data_ready`、DMA 完成回调、队列取包 `*_dequeue`。记 `rx_path[]`（`位置` + 一句话）。
2. **追解析与字段校验**：沿收包追 PDU 头解析（`pdu->hdr.type`、长度字段 `plen`/`hlen`/`pdo`、CmdSN/序号、Header/Data Digest CRC 校验、胶囊 SGL 解析）。每个字段校验点记 `{字段校验, 位置}` 入 `parse_steps[]`。
3. **追业务分发**：定位按报文类型分发的跳转（`switch (pdu->hdr.type)` / opcode 跳转表），记每个类型→处理函数映射入 `dispatch[]`。
4. **追发包路径**：沿处理函数追响应/请求 PDU 的构造与下发（`kernel_sendpage`/`sock_sendmsg`/`.queue_response`、R2T/C2HData/RspCapsule 构造），记 `tx_path[]`。
5. **标畸形处理与可观测**：找非法字段/长度越界/Digest 错/协议违例的处理分支入 `malformed_handling[]`；把收发两侧线上能抓到的报文行为（回何种 PDU、复位、发 Term 请求）入 `observable_wire_behavior[]`。协议错误码成对写"数值+名称"。

## 证据包字段

（字段名对齐 architecture §3 P9："rx_path[] / parse_steps[]{字段校验,位置} / dispatch[] / tx_path[] / malformed_handling[] / observable_wire_behavior[]"）

```yaml
findings:
  rx_path:                       # 收包路径
    - 环节: <如 kernel_recvmsg 收 PDU 头>
      位置: <文件:行号>
  parse_steps:                   # 解析/字段校验步骤
    - 字段校验: <如 校验 hdr.plen 与实际长度一致、Header Digest CRC>
      位置: <文件:行号>
  dispatch:                      # 业务分发
    - 报文类型: <如 nvme_tcp_h2c_data | ICReq | CmdCapsule>
      处理函数: <符号>
      位置: <文件:行号>
  tx_path:                       # 发包路径
    - 环节: <如 构造 R2T PDU 并 kernel_sendpage 下发>
      位置: <文件:行号>
  malformed_handling:            # 畸形报文处理
    - 触发: <如 Header Digest 校验失败 | plen 越界>
      位置: <文件:行号>
      处置: <丢弃 | 回 C2HTermReq | 断链>
  observable_wire_behavior:      # 线上可观测报文行为
    - 现象: <抓包能看到什么，如 回 C2HTermReq(FES=...) 后断链>
      位置: <文件:行号>
```

> 溯源纪律：`findings` 每条必带 `位置: 文件:行号`。协议错误码/常量成对写"数值+名称"（如 `FES=3h Header Digest Error`、`FES=1h Invalid PDU Header Field`）。函数指针分发实际目标不确定处标【推测】入 `inferences[]` 给黑盒验证方法。

## 存储领域示例

> **说明：本节行号为示意虚构，非真实代码锚点，仅示范字段填法。**

对象 `nvmet_tcp` PDU 收发路径：

```yaml
findings:
  rx_path:
    - { 环节: nvmet_tcp_try_recv_pdu 经 kernel_recvmsg 收 PDU 头, 位置: drivers/nvme/target/tcp.c:1108 }
  parse_steps:
    - { 字段校验: 校验 hdr.hlen/plen 合法性与缓冲区边界, 位置: drivers/nvme/target/tcp.c:1130 }
    - { 字段校验: Header Digest CRC32 校验, 位置: drivers/nvme/target/tcp.c:1155 }
  dispatch:
    - { 报文类型: nvme_tcp_h2c_data(H2CData), 处理函数: nvmet_tcp_handle_h2c_data_pdu, 位置: drivers/nvme/target/tcp.c:990 }
    - { 报文类型: nvme_tcp_cmd(CmdCapsule), 处理函数: nvmet_tcp_handle_cmd_pdu, 位置: drivers/nvme/target/tcp.c:945 }
  tx_path:
    - { 环节: 构造 R2T PDU 并 kernel_sendpage 下发请主机送数据, 位置: drivers/nvme/target/tcp.c:1420 }
  malformed_handling:
    - { 触发: Header Digest 校验失败, 位置: drivers/nvme/target/tcp.c:1160, 处置: 回 C2HTermReq 后断链 }
  observable_wire_behavior:
    - { 现象: 收到 Digest 错的 PDU 时回 C2HTermReq(FES=3h Header Digest Error) 并关闭连接, 位置: drivers/nvme/target/tcp.c:1162 }
inferences:
  - claim: 【推测】plen 越界的畸形 PDU 走与 Digest 错不同的处置分支，可能静默断链而不回 Term
    basis: :1130 边界校验失败路径未见构造 C2HTermReq，直接 goto 断链
    verify_method: 构造 plen 超长的畸形 PDU 发给 target，抓包确认是否收到 C2HTermReq 还是直接 RST 断连
```

## 与黑盒观测的接触面

报文收发路径天然贴近黑盒——线上抓包与构造报文正是黑盒的核心手段，本剧本与“primary 用已注册只读工具冻结报文摘要，再将源码关联 obligation 交给同一 worker”的抓包定位流程联动最紧：
- `parse_steps` 的每个字段校验点是 primary 设计**畸形报文用例**的靶点（构造非法长度/错误 Digest/乱序 CmdSN，验证是否按 `malformed_handling` 处置）；
- `observable_wire_behavior` 成对记的"错误码数值+名称 + 回何种 PDU"直接成为用例的**观测判据**（抓包看是否回预期 Term 及其 FES 值）；
- `dispatch` 表让 primary 知道"构造哪类报文能驱动哪条处理路径"，把内部分发翻译成外部可施加的报文激励；不确定的分发目标经 `verify_method` 转为抓包验证，不硬写结论。
