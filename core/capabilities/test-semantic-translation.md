# 白盒到黑盒/灰盒测试语义转译

## 转译链

```text
源码证据 -> 故障模式 -> 外部触发或可控窗口 -> 业务后果
-> 外部观测 -> 排除条件/恢复判据 -> 参数空间 -> 黑盒/灰盒测试场景与用例
```

最终报告和用例以测试人员可执行的语言为主。代码地图、流程和分支章节可保留函数、变量和调用链，但每段源码细节前必须先说明它对应的外部行为、触发条件和风险。

## 风险转译：必须能复现，也能排除

风险卡不是安全攻击故事，也不是白盒诊断结论。每条可执行风险必须闭环：

```text
条件 X 如何构造 -> 系统出现什么结果 Z -> 测试侧如何确认 Z
-> 改成条件 Y 后 Z 是否消失 -> 如何恢复环境
```

- `trigger` 写测试侧可构造的条件 X，不写“攻击者能否利用”，也不把函数名、变量名、锁竞争或源码分支当成唯一触发条件。
- `external_impact` 写系统层面的业务、协议、连接、数据、性能或恢复后果 Z。
- `observation` 至少包含一个外部 PASS/FAIL 判据；TSan、ASan、UBSan、Valgrind 等只能作为辅助证据。
- `recovery` 同时包含恢复动作和排除条件 Y。排除条件用于做对照，验证风险确实由 X 导致，而不是偶发现象。
- 如果只能证明白盒异常，却不知道如何从系统侧构造、观察或排除，则降为 `Developer-confirm`。

## 场景转译：先提取参数空间，再写用例

不能从“认证成功”“连接成功”“升级成功”这种功能标题直接生成一个 Happy Path。必须先从源码和用户材料提取会改变分支、协商、状态或结果的参数维度。

示例结构：

```text
场景：认证建立
参数维度：认证方向 = 单向 | 双向
参数维度：算法 = A | B | C
参数维度：DH/密钥长度 = L1 | L2
参数维度：凭据状态 = 正确 | 错误 | 缺失
```

随后按源码证明的耦合关系展开组合：

- 多个有限维度共同进入同一协商、校验或状态链时，默认展开有效全组合。
- 源码明确证明维度独立时允许缩减，但必须记录缩减理由，并保留边界值和至少一组交叉验证。
- 源码存在成功、失败、缺失、非法、回退或不支持分支时，分别形成覆盖项；不能只覆盖成功路径。
- 每个保留组合至少对应一个可执行用例；用例必须明确自身参数组合，不能用“分别测试所有算法/长度”一句话代替。
- 参数值、边界或不支持关系没有源码/材料证据时写入 `unresolved`，不得用协议常识补齐。

## 转译状态

| 状态 | 适用条件 | 交付 |
|---|---|---|
| `Blackbox-ready` | 外部入口、复现条件、业务判据、排除条件完整 | 可执行黑盒用例 |
| `Graybox-ready` | 需日志、指标、诊断命令、故障注入或测试插桩协助进入条件，但最终结果仍可外部判断 | 可执行灰盒场景/用例 |
| `Developer-confirm` | 仅有代码疑点，缺少可靠外部触发、观测、排除条件或跨仓证据 | 风险卡、代码证据和开发确认问题；不伪造可执行用例 |

## 插桩边界

允许提出系统级测试插桩需求，不生成插桩代码。插桩需求必须包括：

- 要控制的外部可理解窗口或故障条件；
- 内部控制点及其状态/变量/代码位置（可明确写出）；
- 控制语义与参数范围；
- 启停、观测和恢复要求；
- 开发协作责任与用例状态 `待插桩准备`。

示例：将“协议驱动进入报文接收就绪状态”延后 0 到 5 秒，内部控制点为 `iscsi_rsp` 置 TRUE 前；在握手完成后、接收就绪前由主机发送 DATA 报文，验证连接、后续 I/O、协议响应和告警是否按预期恢复。

## 禁止项

- 不生成单元测试、Mock、替换依赖的 Stub、白盒断言或插桩实现代码。
- 不把函数名、变量名或内部接口当成唯一测试步骤；内部名称可作为灰盒说明或插桩定义的一部分。
- 不将源码推测写成已证实的外部缺陷。
- 不以“攻击者”“恶意用户”作为风险测试主体；安全风险同样转成条件、系统结果、观测和排除。
- 不以 Sanitizer 报告替代系统级 oracle。
- 不在 `complete` 分析中只输出 Happy Path 或一个代表性参数组合。
