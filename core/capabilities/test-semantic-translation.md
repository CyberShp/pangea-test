# 白盒到黑盒/灰盒测试语义转译

## 转译链

```text
源码证据 -> 故障模式 -> 外部触发或可控窗口 -> 业务后果
-> 外部观测 -> 恢复判据 -> 黑盒/灰盒测试场景
```

最终报告和用例以测试人员可执行的语言为主。代码地图、流程和分支章节可保留函数、变量和调用链，但每段源码细节前必须先说明它对应的外部行为、触发条件和风险。

## 转译状态

| 状态 | 适用条件 | 交付 |
|---|---|---|
| `Blackbox-ready` | 外部入口、触发和业务判据完整 | 可执行黑盒用例 |
| `Graybox-ready` | 需日志、指标、诊断命令、故障注入或测试插桩协助 | 可执行灰盒场景/用例 |
| `Developer-confirm` | 仅有代码疑点，缺少可靠外部触发、观测或跨仓证据 | 风险卡、代码证据和开发确认问题；不伪造可执行用例 |

## 插桩边界

允许提出系统级测试插桩需求，不生成插桩代码。插桩需求必须包括：

- 要控制的外部可理解窗口或故障条件；
- 内部控制点及其状态/变量/代码位置（可明确写出）；
- 控制语义与参数范围；
- 启停、观测和恢复要求；
- 开发协作责任与用例状态 `待插桩准备`。

示例：将“协议驱动进入报文接收就绪状态”延后 0 到 5 秒，内部控制点为 `iscsi_rsp` 置 TRUE 前；在握手完成后、接收就绪前由主机发送 DATA 报文，验证连接、后续 I/O、协议响应和告警是否按预期恢复。

## 禁止项

- 不生成单元测试、Mock、替换依赖的 Stub、白盒断言或插桩实现代码。
- 不把函数名、变量名或内部接口当成唯一测试步骤；内部名称可作为灰盒说明或插桩定义的一部分。
- 不将源码推测写成已证实的外部缺陷。
