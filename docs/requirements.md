## 1. 产品定位与核心价值

**R-1.1 产品定位**：PANGEA-TEST 是一套面向**存储黑盒测试**的"**测试导航系统**"。它由一组 AI Agent + 平台无关知识资产组成，运行在 codeagent / opencode / Claude Code 等载体上。

**R-1.2 核心价值主张**：Agent 扮演**熟悉模块的资深开发**，服务黑盒测试同学——把代码的内部逻辑"翻译"成**外部可观测行为**（协议报文、CLI 回显、告警、日志），据此产出：
- 代码流程讲解；
- SFMEA（软件失效模式与影响分析）；
- 测试场景；
- 灰盒 / 黑盒测试用例；
- 定位分析（失败用例、日志、抓包）。

> **决策理由**：用户是存储测试工程师，做的是接口卡驱动/带内管理驱动/BMC/CLI/告警/日志等阵列底软的黑盒测试。黑盒测试的最大痛点是"看不见内部"，价值点就在于用代码证据把内部逻辑映射为可从外部触发与观测的行为。因此系统的一切产出都必须落到"外部可观测"上（见 R-7.2）。

**R-1.3 领域范围**：涵盖 NVMe/TCP、iSCSI、NOF、KV、XNET（用户自有协议）、XRT 等协议，以及阵列底软（接口卡驱动、带内管理驱动、BMC、CLI、告警、日志）。示例与用例应优先取自存储领域（如 NVMe/TCP 队列建连、iSCSI CmdSN、连接状态机），避免泛泛的 Web 例子。

## 2. 用户与使用场景

**R-2.1 目标用户**：存储黑盒测试工程师。沟通语言中文；要求技术精确、代码级证据。

**R-2.2 典型工作场景**（对应下游 agent 能力，详见 §4）：
- 模块全量测试分析；
- MR / 问题单分析、FST 逃逸复盘；
- 共性问题排查（一批 MR 或一个现象，搜同类隐患）；
- 专项风险分析；
- 原理/代码流程讲解；
- 日志定位、失败用例三分类、抓包辅助定位；
- 可测试性分析、测试策略、用例评审、缺陷单撰写。

## 3. "导航"的精确定义与边界

**R-3.1 导航 = 四件事（已冻结）**：
1. **意图路由**：识别用户意图，分发到正确的场景族 agent；
2. **输入引导**：缺 MR 要 MR、缺源码路径要路径、缺日志要片段或路径；
3. **场景衔接**：一个场景做完，顺势推荐下一步（如全量分析后推荐专项风险深钻）；
4. **能力菜单展示**：向用户呈现系统能做什么。

**R-3.2 明确排除（禁止复活，见 §12）**：
- 不做 IPD/TR 节点式流程导航；
- 不做项目状态文件；
- 不做测试生命周期跟踪。

> **决策理由**：用户已明确拒绝"流程/项目管理"式导航。本系统的"导航"是**对话内的智能分诊与衔接**，不是项目管理工具。把导航定义收窄到这四件事，可避免系统膨胀成测试管理平台。

## 4. 功能需求

系统采用**三层 agent + 知识资产底座**（架构详见 [architecture.md](architecture.md)）。功能需求按层描述。

### 4.1 Dispatcher（调度层）

- **R-4.1.1**：识别用户意图并路由到场景族 agent；用户也可显式指定场景（显式优先）。
- **R-4.1.2**：输入引导——检测缺失输入并向用户索要（MR、源码路径、日志）。
- **R-4.1.3**：能力菜单展示。
- **R-4.1.4**：场景衔接——完成一个场景后推荐下一步。
- **R-4.1.5**：速度型 / 深度型模式判定（见 R-7.6）。

### 4.2 场景族 agent（人设层，3 个）

- **R-4.2.1 dev-expert（资深开发人设）**：模块全量分析 / MR·问题单分析 / FST 逃逸复盘 / 共性问题排查 / 专项风险 / 原理讲解。
- **R-4.2.2 troubleshooter（定位人设）**：日志定位 / 失败用例三分类 / 抓包辅助定位。
- **R-4.2.3 test-designer（测试设计人设）**：可测试性分析 / 测试策略 / 用例评审 / 缺陷单撰写。

> **决策理由**：族按"人设/职责视角"划分（开发视角、定位视角、测试设计视角），**不按测试生命周期阶段划分**（被否决，见 §12）。场景颗粒度沉在 skill 层——新增一个场景 = 加一个 md，不加 agent（见 R-5.2）。

### 4.3 能力 subagent（脏活层，5 个）

- **R-4.3.1 code-excavator**：单壳 × 挖掘剧本库（详见 §5 与 architecture.md §3）。
- **R-4.3.2 mr-reader**：收编用户已有的 `mr_reader` skill；负责拉取/解析 MR。
- **R-4.3.3 log-miner**：日志挖掘。
- **R-4.3.4 pcap-analyzer**：抓包分析（M3 交付）。
- **R-4.3.5 auditor**：独立审查（Judge），独立视角复核产出与覆盖。

**R-4.3.6 能力 subagent 四判据**（新增能力 subagent 必须同时满足）：① 过程高噪音；② 多场景复用；③ 产出可压缩成证据包；④ 需要独立视角（此条是 auditor 的入选理由）。

> **决策理由**：脏活（大量读码、grep、日志翻找）噪音高、上下文消耗大，抽成 subagent 后：主对话上下文干净、能并行、产出可复用可断点。四判据是准入门槛，防止 subagent 层无序膨胀。

### 4.4 场景族与能力层的关系

- **R-4.4.1 交接工件（证据包）**：场景族 agent 调用能力 subagent，subagent 回传"证据包"（压缩后的结构化产出），兼作深度模式的断点。
- **R-4.4.2 深度模式标准形态 = 多实例并行 fan-out**：例如 dev-expert 做全量分析时，并行派发 主干追踪 ∥ 异常传播 ∥ 资源生命周期 ∥ 风险×并发 四个 code-excavator 实例，各自独立上下文，回收证据包后汇总。

## 5. 架构性需求（约束）

**R-5.1 铁律"agent 薄、skill 厚"**：agent 定义只是壳（人设一句话 + 声明加载哪些 skill/工具），全部流程、模板、知识放在**平台无关的纯 md**。跨平台移植只重写薄适配层。

**R-5.2 场景颗粒度沉在 skill 层**：加场景 = 加一个 md，不加 agent。

**R-5.3 code-excavator = 单壳 × 挖掘剧本库**：
- 不做多个特化挖掘 agent；一个 `code-excavator` 壳（工具集 + 溯源铁律 + 证据包纪律）。
- 锋利度来自**派发时注入的剧本**（playbook）。
- **结构类剧本**（挖"是什么"，每剧本一个 md + 专属证据包 schema）初稿清单：入口与主干追踪、分支全枚举、状态机提取、资源生命周期配对、异常传播路径、调用链与影响域、并发上下文识别（共享数据/锁边界/执行流清单）、超时与重试点盘点、协议报文收发路径（socket 收包→业务处理全链路，存储协议特色）。清单为初稿，执行时可扩展，交用户审。
- **风险类**：不单独写剧本。通用"风险扫描"流程 × 透镜驱动——`excavator(对象, 风险扫描, 透镜=资源泄漏)`，透镜文件中"代码特征模式"栏即扫描指令。
- **升格允许**：实测表现差的剧本，允许升格为独立 agent，架构允许两种形态共存。

> **决策理由**：多个特化挖掘 agent 会导致壳爆炸、维护成本高、能力重叠。"单壳 × 剧本库"把差异沉到纯 md 剧本里，加挖掘能力 = 加剧本，不动 agent。这与 R-5.1/R-5.2 一脉相承。

**R-5.4 知识资产平台无关**：`scenarios/ lenses/ methods/ playbooks/ templates/ shared/ protocols/ modules/` 必须是平台无关纯 md。

## 6. 知识资产需求

**R-6.1 两库正交设计（已冻结）**：`lenses/` 与 `methods/` 是正交的两个库，组合使用。
- **lenses/（DFX 风险透镜库）回答"找什么风险"**，被 SFMEA 与风险用例消费。
- **methods/（测试设计方法论库）回答"怎么系统性推导用例"**，被用例生成步骤消费。
- 正交组合示例：连接状态机 → 透镜层扫出"超时恢复"风险（定优先级），方法论层选"状态转换法"推导用例（保完备性）。

**R-6.2 lenses/ 详细需求**：
- 按团队 DFX 维度归类：可靠性（异常处理、数据完整性、恢复路径）、可用性、性能、规格（对外规格 / 内部实现规格）、韧性、可服务性（正常/异常/告警/日志/性能统计/错误码/搜索/批量/名称查询操作/前向版本兼容）、升级。
- **全部维度内容由 Claude 出初稿，且不局限于用户列出的条目**（用户原话），用户后改。
- 每个透镜文件骨架：**风险机理 / 代码特征模式（excavator 扫描指引）/ 典型历史缺陷（团队回填位）/ 黑盒触发手段 / 观测判据 / 用例骨架**。
- **透镜双消费模式**：
  - 全量分析场景 = **全透镜浅扫**（每个透镜过一遍，有特征→入 SFMEA，无特征→一句话说明免疫理由）；
  - 专项风险场景 = **单透镜深钻**到用例级。

**R-6.3 methods/ 详细需求**：
- 12 个方法论各一文件 + `_selector.md` 选择表（测试点特征 → 适用方法）。
- 12 方法论：等价类划分、边界值分析、数据组合测试、判定表覆盖、判定点覆盖、处理周期测试、状态转换、数据生命周期、错误推测、端到端场景、MAE 流程覆盖、时间维度覆盖。
- 每个文件骨架：**适用特征（agent 识别信号）/ 操作步骤 / 存储领域示例 / 产出映射**。

**R-6.4 可服务性清单双重身份**：既是 lenses/ 中的一个透镜，又是**黑盒观测手段目录**（族1/族2 写观测判据时从中选手段）。单独成文，两处引用。

> **决策理由**：风险发现（找什么）与用例推导（怎么推）是两个正交问题，混在一起会导致"知道有风险但推不全用例"或"用例很多但没对准风险"。两库分离后可自由组合。透镜双消费保证全量分析广度覆盖、专项分析深度覆盖。lenses/methods 初稿由 Claude 出、团队回填，是"骨架我搭、血肉你填"的分工。

## 7. 全局铁律（非功能需求，写进 shared/，所有 agent 遵守）

**R-7.1 溯源双轨制**：事实必须引用 `文件:行号` 或日志/报文原文；推断必须标【推测】并附验证方法；无证据不下结论。

**R-7.2 黑盒可执行性**：每条用例必须写清"用什么外部手段触发、观测什么外部现象判 PASS/FAIL"，禁止出现黑盒做不到的步骤（如"检查内部状态机变量"）。

**R-7.3 格式不擅改**：黑盒用例格式由 `templates/黑盒用例.md` 统一控制，Agent 不得擅自改变用户已有格式（继承自 Codetalks）。

**R-7.4 知识优先级**：references 有对应知识文件先读，没有再现场读码；每次分析收尾询问用户是否将结论回填（透镜的"典型历史缺陷"栏、`protocols/`、`modules/` 知识文件）。

**R-7.5 MCP 泛化探测**：探测到 codehub 类 MCP 工具则用其拉 MR；没有则请用户粘贴 diff + MR 描述。**不硬编码具体工具名。**

**R-7.6 双模式**：
- 速度型 = 族 agent 内联执行、不落中间工件；
- 深度型 = 走能力 subagent、每步落交接工件（兼断点恢复）、收尾过 auditor + 覆盖审计。

**R-7.7 输出中文**，报告落 Markdown 文件。

> **决策理由**：这七条是全系统的质量地基，直接继承自 Codetalks 的成熟实践。溯源双轨制与黑盒可执行性是"代码级证据 + 黑盒可落地"的双保险，是本系统区别于普通"AI 讲代码"的核心。

## 8. 输入约定（已冻结）

- **R-8.1**：问题单/FST 场景——只给 MR 链接，问题背景由 Agent 从 MR 描述读取。
- **R-8.2**：共性问题排查——一批 MR 链接 **或** 问题现象描述（Agent 搜码找同类隐患），两者都支持。
- **R-8.3**：日志定位——粘贴片段 **或** 给文件路径（Agent 自行 grep，文件可能很大）。
- **R-8.4**：全量分析/原理讲解——询问用户是否基于源码分析，是则索要源码路径。
- **R-8.5**：场景路由——Dispatcher 意图识别为主，用户也可显式指定场景。

## 10. 迁移需求与内外网分工

**R-10.1 Codetalks 是核心迁移源**。迁移映射（详见 architecture.md 与 handover §6）：

| Codetalks 资产 | 归宿 |
|---|---|
| 八问分析纲领 | `shared/` dev-expert 分析框架 |
| 九步链路 | 族1 场景 skill 主干（全量分析用全链路，MR 分析用裁剪版）|
| 模块全量测试分析、问题单/MR 回归分析 | 族1 场景 skill，**逐字继承改造而非重写** |
| 问题根因辅助定位 | 族2 场景 skill 核心流程 |
| 专项风险分析 | 透镜库条目 + 族1 专项风险场景 |
| 黑盒用例.md 格式控制 | `templates/` + 铁律 R-7.3 |
| 覆盖审计、Coverage Gate | 产出型场景收尾质量门 |
| 深度型分步保存工件 + compact 恢复 | 交接工件 + 断点恢复机制 |
| 独立 Judge | auditor subagent |
| 速度/深度双模式 | Dispatcher 分发参数 |

**R-10.2 内外网分工（关键约束）**：Codetalks 原文件、现有 `黑盒用例.md`、`mr_reader` 原文件均为**内部资产，不会提供给本次执行环境**。因此：
- 涉及迁移的部分**只搭骨架**，留 `<!-- 待迁移：内网环境完成 -->` 占位，**不得凭简介重写迁移内容**；
- `黑盒用例.md` 写一份通用版（标注"占位，内网替换为团队版"）；
- `mr-reader` 只写接口壳：输入（MR 链接/粘贴 diff）与输出证据包 schema，内部实现留占位；
- 所有占位点汇总成一份《内网待办清单》（见 architecture.md 末尾），供用户带回 codeagent 环境逐项完成。

> **决策理由**：内网资产不可外传，凭简介重写会产生"看似完成实则失真"的假迁移，污染后续团队回填。故一律留占位、集中清单，把真迁移留在有原文件的环境完成。

## 11. 交付范围与里程碑

**R-11.1 M1（首个里程碑，骨架可跑）**：
- Dispatcher + dev-expert 族 agent（opencode 格式）；
- code-excavator 壳 + 5 个核心剧本（主干追踪 / 分支枚举 / 状态机提取 / 资源生命周期 / 异常传播）+ 风险扫描通用流程（配种子透镜，即"5+1"）；

## 12. 被否决的设计（禁止复活）

以下方案已被用户明确否决，**任何后续迭代不得复活**：

1. **IPD/TR 节点式流程导航**——导航不是流程管理。
2. **项目状态文件**——不做状态持久化式项目跟踪。
3. **测试生命周期跟踪**——不做生命周期跟踪。
4. **按视角拆多个挖掘 agent**——挖掘用"单壳 × 剧本库"，不拆多 agent（R-5.3）。
5. **按测试生命周期分族**——族按人设/职责视角分（dev-expert / troubleshooter / test-designer），不按生命周期阶段分。

> **决策理由**：集中记录否决项，是为了让未来的执行者（人或 Agent）在"看起来很自然"的时刻不会不自觉地把它们重新引入。遇到疑似需要复活的强需求，应停下问用户，而非自行裁定（见执行纪律 handover §10）。
